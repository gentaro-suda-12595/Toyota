# 開発ガイドライン (Phase 1 〜 Phase 4)

## Phase 1: データ生成とスキーマ進化 (Schema Evolution)
1.  **初期データロード (Aさん):** Python (`Faker` ライブラリ等) を用いて架空の従業員データ1万件を生成し、Bronze層 (`bronze_hr_employees`) に保存する。Silver層への初期書き込みパイプラインも構築する。
2.  **スキーマ変更のシミュレーション (Aさん):** データ生成ロジックを変更し、翌日の差分データとして新カラム `bonus`（ボーナス金額）を含めたデータをBronze層に追加する。
3.  **スキーマの自動追従 (Aさん):** Silver層への書き込み処理に `mergeSchema = True` を組み込み、パイプラインを停止させることなく新しい `bonus` カラムをSilverテーブルに反映させる。

## Phase 2: Change Data Feed (CDF) による差分伝播
1.  **CDFの有効化 (Aさん):** Silverテーブルのプロパティ設定で `delta.enableChangeDataFeed = true` を適用する。
2.  **データ変更の実行 (A・Bさん):** Silverテーブルに対して、任意の従業員の給与更新 (UPDATE) と退職処理 (DELETE) を数件実行する。
3.  **増分更新パイプラインの構築 (Aさん):** `table_changes('silver_hr_employees', <version>)` 関数を使用して変更履歴のみを読み取り、Gold層の集計テーブル (`gold_dept_metrics`) へ効率的に `MERGE INTO` して数値を更新する。

## Phase 3: Time Travel と障害復旧 (RESTORE)
1.  **データ破壊シミュレーション (Bさん):** 意図的にWHERE句を省略したUPDATE文を実行し、Silver層の全従業員の `salary` を `0` に変更する。
2.  **履歴の確認 (Bさん):** `DESCRIBE HISTORY silver_hr_employees` を実行し、データが破壊される前のバージョン番号またはタイムスタンプを特定する。
3.  **復旧作業 (Bさん):** `RESTORE TABLE` コマンドを用いて、Silverテーブルを正常な状態（破壊前のバージョン）にロールバックする。

## Phase 4: Unity Catalog による動的アクセス制御
1.  **行フィルターの実装 (Aさん):** `current_user()` やグループ判定ロジックを用いて、クエリ実行者の担当リージョン（例: AさんはJapan、BさんはUS）のレコードのみを返すSQL関数を作成し、Silverテーブルに行フィルターとして適用する。
2.  **列マスクの実装 (Aさん):** 特権グループ以外のユーザーがアクセスした場合、`salary` カラムの値を `0` または `NULL` で返し、`ssn` カラムの値を `***-**-1234` のように難読化するSQL関数を作成し、Silverテーブルに列マスクとして適用する。
3.  **監査と検証 (Bさん):** BさんのアカウントでSilverテーブルに対して `SELECT` を実行し、他リージョンのデータが除外されていること、および `salary` と `ssn` が正しくマスキングされていることを確認する。
